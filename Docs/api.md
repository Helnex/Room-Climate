# Контракт API

Материалы лабораторной работы № 7. Формальный контракт — **[api/openapi.yaml](api/openapi.yaml)**
(OpenAPI 3.0.3). Открыть как документацию: https://editor.swagger.io → File → Import URL →
`https://raw.githubusercontent.com/Helnex/Room-Climate/main/Docs/api/openapi.yaml`
(или вставить содержимое файла). Работающий сервер дополнительно публикует полную
автоматическую документацию по адресу `http://<стенд>:8000/docs`.

## 1. Граница API

Сетевой API проходит между отдельными программами на разных устройствах
(см. [architecture.md](architecture.md)):

| Стык | Интерфейс | Кто клиент | Авторизация |
|---|---|---|---|
| Android-приложение ↔ сервер | IКлиентское API | «Сетевой клиент» приложения | Bearer-токен сессии |
| Плата Raspberry Pi ↔ сервер | IПриём измерений | «Сборщик показаний» | Заголовок `X-Device-Token` |

**Внутренние вызовы, которые не становятся сетевым API:** модули сервера («Аккаунты и
доступ», «Пороги», «Показания и история», «Помещения и устройства») работают в одном процессе
FastAPI и вызывают друг друга как функции Python — например, проверка прав на плату
(`access.check`) вызывается напрямую из обработчиков порогов и истории. Превращать её в
HTTP-запрос не нужно: это добавило бы задержку, точку отказа и сериализацию без пользы,
потому что модули и так выпускаются вместе. Внутри приложения экраны тоже вызывают
«Сетевой клиент» напрямую. Обработчик связан с API через очередь Redis, а не через HTTP.

## 2. Ресурсы и эндпоинты (ядро MVP)

| Метод и адрес | Назначение | История |
|---|---|---|
| `POST /auth/register` | Зарегистрироваться и получить токен сессии | US-08 |
| `POST /auth/login` | Войти и получить токен сессии | US-08 |
| `POST /telemetry` | Плата передаёт пакет показаний | US-01, US-02 (FR-01, FR-02) |
| `GET /telemetry/current?device_id=` | Текущие показания платы | US-01 |
| `GET /telemetry/history?device_id=&from=&to=` | История показаний за период | US-02 |
| `GET /settings?device_id=` | Пороги уведомлений платы | US-03 |
| `PUT /settings?device_id=` | Сохранить пороги (заменить целиком) | US-03, US-07 |
| `GET /rooms` | Список помещений с текущими показаниями | US-05 |
| `POST /rooms` | Создать помещение (и привязать плату) | US-05 |
| `PATCH /rooms/{room_id}` | Переименовать помещение | US-06 |
| `DELETE /rooms/{room_id}` | Удалить помещение | US-05 |

Ресурсы — существительные предметной области из лабораторных № 2–3: показания (`telemetry`),
пороги (`settings`), помещения (`rooms`). Действие выражено методом: `GET` — получить,
`POST` — создать/передать, `PUT` — заменить пороги целиком, `PATCH` — изменить одно поле
помещения, `DELETE` — удалить. Авторизация (`/auth/...`) — исключение из чистого REST: это
действия над сессией, такие адреса приняты повсеместно.

## 3. Данные и коды ответов

**Основные схемы** (полностью — `components/schemas` в `openapi.yaml`):

| Схема | Поля (обязательные выделены) |
|---|---|
| `TelemetryIn` | **device_id** (строка, `[A-Za-z0-9_.-]`, ≤ 64), **readings** (1–32 × `Reading`), measured_at (дата-время, только при досылке) |
| `Reading` | **type** (показатель из справочника), **value** (конечное число), **unit** (≤ 16) |
| `CurrentTelemetry` | **device_id**, **source** (`redis` / `sqlite`), **readings** — словарь «показатель → {value, unit, measured_at}» |
| `History` | **device_id**, **count**, **points** — массив {type, unit, value, measured_at} |
| `SettingsIn` | **temp_min**, **temp_max** (−100…200), humidity_min, humidity_max (0…100); min < max |
| `Settings` | поля `SettingsIn` + **device_id**, **saved** |
| `RoomIn` / `Room` | **name** (1–40 символов), board_id / **id**, **name** |
| `AuthResponse` | **id**, **email**, **name**, **surname**, **token** |
| `Error` | **detail** — понятное сообщение на русском |

**Коды ответов.**

| Код | Когда | Пример тела |
|---|---|---|
| 200 | Успех (в том числе создание помещения — см. раздел 5) | — |
| 400 | Нарушено правило предметной области: минимум не меньше максимума | `{"detail": "Минимальная температура должна быть меньше максимальной"}` |
| 401 | Нет или недействителен токен сессии / токен устройства; неверный пароль | `{"detail": "Сессия недействительна, войдите заново"}` |
| 403 | Действие запрещено (участник доступа не может распоряжаться чужой платой; регистрация из интернета без кода) | `{"detail": "Это может сделать только владелец платы"}` |
| 404 | Объекта нет **или он чужой** — чтобы перебором нельзя было узнать чужие платы | `{"detail": "Устройство не найдено"}` |
| 409 | Конфликт: email или название помещения уже заняты | `{"detail": "Помещение с таким названием уже есть"}` |
| 422 | Данные не прошли проверку формата: пустое поле, не число, неизвестный показатель | `{"detail": "Минимальная температура: ожидается число"}` |
| 429 | Слишком много попыток входа | `{"detail": "Слишком много запросов. Подождите минуту."}` |
| 503 | Недоступно хранилище текущих значений (Redis) | `{"detail": "Redis недоступен"}` |

Почему такое тело ошибки: одно поле `detail` с готовым текстом на русском приложение
показывает пользователю без разбора, а код ответа служит машиночитаемым признаком.
Английские сообщения FastAPI/pydantic сервер переводит (модуль `errors.py`), поэтому
клиенту никогда не приходит «сырой» список ошибок валидации.

**Пример.** `PUT /settings?device_id=pi-1` с телом `{"temp_min": 25, "temp_max": 24}` →
`400 {"detail": "Минимальная температура должна быть меньше максимальной"}`, сохранённые
пороги не меняются.

## 4. Спецификация OpenAPI

Фрагмент `openapi.yaml` — операция сохранения порогов и схема ошибки:

```yaml
  /settings:
    put:
      tags: [Пороги]
      summary: Сохранить пороги уведомлений платы
      operationId: putSettings
      parameters:
        - $ref: "#/components/parameters/DeviceId"
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: "#/components/schemas/SettingsIn" }
      responses:
        "200":
          description: Пороги сохранены
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Settings" }
        "400":
          description: Минимум не меньше максимума
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Error" }
        "401": { $ref: "#/components/responses/Unauthorized" }
        "404": { $ref: "#/components/responses/DeviceNotFound" }
        "422": { $ref: "#/components/responses/ValidationError" }
components:
  schemas:
    Error:
      type: object
      properties:
        detail: { type: string, example: "Минимальная температура должна быть меньше максимальной" }
      required: [detail]
```

**Проверка валидности:** спецификация проходит валидатор `openapi-spec-validator`
(OpenAPI 3.0.3, 8 путей, 11 операций) и без ошибок открывается в Swagger Editor
(скриншот — в отчёте, `Reports/images/lab7-swagger.png`). Соответствие сервера контракту
проверяет автотест `roomclimate/server/test_contract.py` в CI: каждая операция контракта
существует на сервере, обязательные поля запросов совпадают со схемами pydantic, реальные
ответы содержат обязательные поля схем, ошибки приходят в формате `Error`.

## 5. Версия и безопасность

- **Версия контракта — 1.0.0** (`info.version`). Префикс `/v1` в путях не вводился: API уже
  используют выпущенные версии приложения и платы, а смена адресов сломала бы их. Правило
  команды: совместимые изменения (новые необязательные поля, новые эндпоинты) — повышение
  минорной версии без смены адресов; несовместимые — только под новым префиксом `/v2` при
  сохранении старых путей. Пример: создание помещения возвращает 200, а по REST правильнее
  201 — исправление отложено до `/v2`, чтобы не сломать клиентов.
- **Безопасность:** `bearerAuth` (токен сессии, 30 дней) для всех операций приложения, кроме
  входа и регистрации; `deviceToken` (заголовок `X-Device-Token`) для приёма показаний.
  Секреты (`INGEST_TOKEN`, коды приглашения, пароли SMTP) хранятся в `server/.env`, который
  исключён из git; в спецификации — только имена схем авторизации.

## 6. План параллельной работы

- **Серверная сторона** — Кобзев С. (модули API), Крючков К. (стенд, CI, контрактный тест).
  **Клиентская сторона** — Вековшинин И. («Сетевой клиент», уведомления), Камалетдинов М.
  (экраны). **Плата** — Хабарова А. (клиент IПриём измерений).
- Изменение API начинается с правки `openapi.yaml` в отдельном pull request: его просматривают
  представители обеих сторон. После слияния стороны работают одновременно: клиент — на
  заглушке, которая отдаёт JSON из `example` спецификации (например, Prism:
  `npx @stoplight/prism-cli mock Docs/api/openapi.yaml`), сервер — реализует эндпоинт и
  проверяет его `test_contract.py`.
- Стыковка — к концу спринта: интеграционный тест приложения `LiveServerIntegrationTest`
  в `android-ci` ходит в настоящий сервер, поднятый в том же прогоне CI, и сразу показывает
  расхождение. Задачи «контракт», «сервер», «клиент» заводятся отдельными карточками на
  доске ([sprints.md](sprints.md)) со связью «клиент зависит от контракта», а не от сервера.
- `openapi.yaml` — **единый источник правды**: менять поведение API в одностороннем порядке
  нельзя; если реализация расходится с контрактом, CI становится красным.
