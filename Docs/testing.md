# Тестирование RoomClimate

Материалы лабораторной работы № 5: объём тестирования, тестовые сценарии, сквозной
сценарий и спецификации unit-тестов «вход → ожидаемый выход». Сценарии построены на
критериях приёмки из [requirements.md](requirements.md), модули названы так же, как в
[architecture.md](architecture.md).

## 1. Объём тестирования

Проверки относятся к ядру MVP.

| Возможность (история) | Модули, которые проверяются |
|---|---|
| US-01. Текущие показатели | Сборщик показаний, Приём телеметрии, Показания и история, Экраны |
| US-02. График за сутки | Показания и история, Экраны (в сквозном сценарии) |
| US-03. Диапазон уведомлений | Пороги |
| US-04. Уведомление о выходе за диапазон | Обработчик → Проверка порогов, ntfy |
| US-08. Личный аккаунт | Аккаунты и доступ |

Не входят в эту работу: Should/Could-возможности (помещения, общий доступ, CSV, виджеты) —
для них есть отдельные автотесты (`test_home.py`) и ручной чек-лист
[QA/Devices-Test-Plan.md](QA/Devices-Test-Plan.md).

**Классы случаев**, которые проверяются для каждой ключевой операции: успешный; отрицательный
(некорректные данные, нет доступа, отказ зависимости); граничный (значение на границе
диапазона, повторное действие, равные минимум и максимум).

## 2. Тестовые сценарии

**TS-01 (US-03, успешный).**
> **Дано:** пользователь вошёл, у платы `pi-1` пороги по умолчанию 18…26 °C.
> **Когда:** на экране «Пороги» вводит минимум 20 и максимум 24 и нажимает «Сохранить пороги».
> **Тогда:** показывается подтверждение; после закрытия и повторного открытия экрана в полях 20 и 24.

**TS-02 (US-03, отрицательный).**
> **Дано:** сохранены пороги 20…24 °C.
> **Когда:** пользователь вводит минимум 25 и максимум 24 и сохраняет.
> **Тогда:** сообщение «Минимальная температура должна быть меньше максимальной»; после повторного открытия экрана по-прежнему 20 и 24.

**TS-03 (US-03, граничный).**
> **Дано:** сохранены пороги 20…24 °C.
> **Когда:** пользователь вводит минимум 24 и максимум 24.
> **Тогда:** та же ошибка, значения не меняются.

**TS-04 (US-04, успешный).**
> **Дано:** пороги 18…26 °C, на телефоне разрешены уведомления, приложение закрыто.
> **Когда:** датчик нагревают до 27 °C и держат 2 минуты.
> **Тогда:** приходит ровно одно уведомление «Температура вне нормы. Плата pi-1: температура 27,… °C — выше порога 26,0 °C»; в журнале тревог одна открытая тревога.

**TS-05 (US-04, граничный).**
> **Дано:** пороги 18…26 °C.
> **Когда:** температура 27 °C держится 30 с и опускается до 24 °C.
> **Тогда:** уведомления нет, журнал тревог пуст.

**TS-06 (US-01, отрицательный).**
> **Дано:** пользователь вошёл, сервер выключен.
> **Когда:** пользователь открывает главный экран.
> **Тогда:** сообщение об ошибке связи и последние сохранённые значения с пометкой времени; приложение не закрывается; после включения сервера значения обновляются сами.

**TS-07 (US-08, отрицательный).**
> **Дано:** пользователь зарегистрирован с паролем `secret12`.
> **Когда:** вводит пароль `wrong-pass`.
> **Тогда:** сообщение «Неверный email или пароль», вход не выполнен; после 10 неудачных попыток за 15 минут — «Слишком много неудачных попыток входа. Попробуйте через 15 мин.».

## 3. Сквозной сценарий

**E2E-01. Главный путь пользователя (US-08 → US-01 → US-03 → US-04 → US-02).**

| Шаг | Действие и ожидаемый результат | Модули |
|---|---|---|
| 1 | Исходно: стенд запущен, плата `pi-1` с DHT22 включена в комнате, у пользователя нет аккаунта. | — |
| 2 | Пользователь регистрируется в приложении → открывается главный экран. | Экраны → Сетевой клиент → Аккаунты и доступ → SQLite |
| 3 | На главном экране видны текущие температура (≈ 23 °C) и влажность, статус «На связи»; через 15 с значения обновляются. | Сборщик показаний → Приём телеметрии → Redis → Показания и история → Экраны |
| 4 | Пользователь сохраняет пороги 18…26 °C; попытка «25…24» отклоняется с ошибкой. | Экраны → Пороги → SQLite |
| 5 | Приложение закрывается; датчик нагревают выше 26 °C дольше минуты. | Сборщик → Приём телеметрии → Очередь → Обработчик |
| 6 | Приходит одно уведомление «Температура вне нормы… выше порога 26,0 °C». | Проверка порогов → ntfy → приложение ntfy |
| 7 | Пользователь открывает «Графики → 24 часа» и видит всплеск температуры. | Экраны → Показания и история → SQLite |
| 8 | Датчик остывает до 25 °C и ниже → приходит «Температура: снова в норме», повторных тревог нет. | Проверка порогов → ntfy |

**Итог:** не подходя к датчику, пользователь знает текущий климат, получил предупреждение о
выходе за свой диапазон и видит, когда это произошло. Шаги 2–4 и 7 частично автоматизированы
интеграционным тестом приложения `LiveServerIntegrationTest` (Android, JUnit) и смоук-тестом
сервера `smoke_test.py`, которые CI запускает на поднятом стеке Docker.

## 4. Спецификации unit-тестов

Все спецификации ниже реализованы в коде (колонка «Автотест») и прогоняются в CI на каждый
pull request — см. [ci-cd.md](ci-cd.md).

| № | Модуль / операция | Вход (данные и исходное состояние) | Ожидаемый выход | Класс | Автотест |
|---|---|---|---|---|---|
| UT-01 | Пороги / сохранить | Плата без порогов; `temp_min=20, temp_max=24` | 200, `saved=true`; чтение порогов возвращает 20 и 24 | успешный | `server/test_lab_specs.py` |
| UT-02 | Пороги / сохранить | Сохранены 20…24; `temp_min=25, temp_max=24` | 400, `{"detail": "Минимальная температура должна быть меньше максимальной"}`; сохранены по-прежнему 20…24 | отрицательный | то же |
| UT-03 | Пороги / сохранить | `temp_min=24, temp_max=24` | 400; пороги не сохранены (`saved=false`) | граничный | то же |
| UT-04 | Пороги / сохранить | `temp_max=300` | 422, сообщение «Максимальная температура: должно быть не больше 200.0» | отрицательный | то же |
| UT-05 | Пороги / сохранить | `temp_min=-100, temp_max=200` (края диапазона) | 200, значения приняты | граничный | то же |
| UT-06 | Пороги / прочитать | Плата без сохранённых порогов | 18 °C, 26 °C, `saved=false` | успешный | то же |
| UT-07 | Проверка порогов / следующее состояние | Состояние «норма», 26,2 °C, порог 18…26, гистерезис 0,5 | «выше порога» | успешный | то же |
| UT-08 | Проверка порогов / следующее состояние | «выше порога», 25,8 °C | остаётся «выше порога» (внутри гистерезиса) | граничный | то же |
| UT-09 | Проверка порогов / следующее состояние | «выше порога», 25,5 °C | «норма» | граничный | то же |
| UT-10 | Проверка порогов / обработать измерения | 27 °C в 0 с и 30 с, затем 24 °C | открытых тревог нет | граничный | то же |
| UT-11 | Проверка порогов / обработать измерения | 27 °C каждые 10 с в течение 120 с | ровно одна открытая тревога, текст содержит «выше порога 26,0» | успешный | то же |
| UT-12 | Обработчик / обработать сообщение очереди | 13 досланных (`late=1`) показаний 30 °C за 120 с | 13 измерений в истории, тревог нет | отрицательный | то же |
| UT-13 | Приём телеметрии | Пакет с показателем `radiation`, которого нет в справочнике | 422, «Неизвестный показатель: radiation…» | отрицательный | то же |
| UT-14 | Приём телеметрии | Пустой список показаний | 422 | граничный | то же |
| UT-15 | Приём телеметрии | Корректный пакет, Redis недоступен | 503, «Redis недоступен» | отрицательный | то же |
| UT-16 | Аккаунты и доступ / вход | Существующий email, неверный пароль | 401, «Неверный email или пароль» | отрицательный | то же |
| UT-17 | Аккаунты и доступ / проверка сессии | Запрос порогов без заголовка `Authorization` | 401 | отрицательный | то же |
| UT-18 | Аккаунты и доступ / доступ к плате | Плата закреплена за владельцем; запрос постороннего | 404, «Устройство не найдено» (существование чужой платы не раскрывается) | отрицательный | то же |
| UT-19 | Приём телеметрии / токен устройства | На сервере задан токен платы; запрос без токена и с неверным | 401, «Неверный токен устройства» | отрицательный | то же |
| UT-20 | Сборщик показаний / проверка правдоподобия | 22,4 °C; 45 % | значение отправляется (`True`) | успешный | `collector/test_lab_specs.py` |
| UT-21 | Сборщик показаний / проверка правдоподобия | −40 °C и 0 %; 80 °C и 100 % | `True` (границы DHT22 включены) | граничный | то же |
| UT-22 | Сборщик показаний / проверка правдоподобия | 80,1 °C; −40,1 °C; 100,1 % | `False` — сбой чтения, на сервер не отправляется | отрицательный | то же |
| UT-23 | Сборщик показаний / проверка правдоподобия | Температура или влажность отсутствует (`None`) | `False` | отрицательный | то же |

Дополнительно в репозитории есть ранее написанные автотесты: тревоги и «датчик молчит»
(`server/test_alerts.py`), помещения и доступ (`server/test_home.py`), плата и досылка
(`server/test_board.py`), справочники и миграции (`server/test_registry.py`), 8 наборов
тестов сборщика (`collector/test_*.py`) и 34 JUnit-теста приложения, в том числе
`ThresholdCheckerTest`, `HysteresisTest`, `FormattersTest`. Контракт API проверяется
тестом `server/test_contract.py` (см. [api.md](api.md)).

## 5. Запуск

```powershell
cd roomclimate/server
python -m unittest -v test_lab_specs      # UT-01…UT-19
python -m unittest -v test_contract       # соответствие openapi.yaml (нужен PyYAML)
cd ../collector
python test_lab_specs.py                  # UT-20…UT-23
```

Результат последнего локального прогона (26.11.2026, Python 3.13, Windows):
`test_lab_specs` — 19 тестов OK; `test_contract` — 6 тестов OK; сборщик — 4 теста OK.

## 6. Definition of Done

Задача считается готовой, когда: критерии приёмки истории выполнены; для изменённой логики
добавлены или обновлены автотесты; CI в pull request зелёный; изменение просмотрел хотя бы
один участник; при изменении API обновлён `openapi.yaml`. Сценарии TS-01…TS-07 и E2E-01
проходит тестировщик (Камалетдинов М.) на телефоне перед демонстрацией спринта.
