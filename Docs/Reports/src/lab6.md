# Ответы на контрольные вопросы

**1. Что такое непрерывная интеграция и почему изменения выгодно вливать часто и небольшими
порциями? Как это связано с «интеграцией большим взрывом»?**

CI — практика частого слияния изменений в общую ветку, при которой каждое изменение
автоматически собирается и проверяется тестами. Маленькое изменение легко просмотреть, а
если оно что-то сломало, причина очевидна и исправление занимает минуты. При «большом
взрыве» участники неделями работают отдельно, и при слиянии всплывают десятки
несовместимостей сразу. В нашем проекте с 22.10 по 26.11 влит 21 pull request; на каждый
GitHub Actions собирает сервер и приложение и прогоняет тесты, в том числе интеграционный
тест приложения с живым сервером.

**2. Что означают «зелёная» и «красная» сборка? Почему основную ветку держат зелёной и
почему красную сборку чинят в первую очередь?**

Зелёная — проект собрался и все тесты прошли; красная — что-то из этого упало. Из `main`
все создают ветки и с неё обновляется стенд; если `main` красная, у каждого, кто от неё
отталкивается, ломается работа, а новые ошибки прячутся за уже существующей. Поэтому
красную сборку чинят в первую очередь — пример из истории проекта: на `ubuntu-latest`
перестал собираться `pydantic-core`, CI стал красным, и первым делом в пайплайн закрепили
Python 3.11 (PR #15).

**3. Из каких шагов состоит ваш пайплайн и в каком порядке они идут? Почему «от дешёвого к
дорогому»?**

`server-ci`: получить код → установить Python 3.11 → установить зависимости → unit-тесты по
спецификациям → контрактный тест OpenAPI → остальные unit-тесты → собрать и поднять стек
Docker Compose → смоук-тест живого API → остановить стек. Быстрые проверки (секунды) идут
раньше медленных (сборка образов, запуск контейнеров): если сломано правило порогов, мы
узнаём это через несколько секунд и не тратим минуты на сборку Docker. `android-ci` —
отдельный пайплайн, потому что сборка APK самая долгая.

**4. Как связаны pull request, автоматические проверки и защита основной ветки? Что не даёт
сломанному коду попасть в main?**

Pull request — единственный путь изменений в `main`; на его открытие и каждое обновление
запускаются пайплайны, статус которых виден в PR. Защита ветки делает зелёный статус
обязательным условием: при красной проверке кнопка слияния недоступна, а без одобрения
ревьюера PR тоже не влить. Сломанный код задерживают три барьера: тесты в CI, ревью коллеги
и правило защиты ветки, которое не позволяет обойти первые два.

**5. Почему секреты нельзя коммитить в репозиторий и где их хранят?**

Всё, что попало в git, остаётся в истории навсегда, даже если файл потом удалить, а наш
репозиторий публичный — любой мог бы, например, отправлять поддельные показания с токеном
платы или публиковать APK. Секреты хранятся в `server/.env` (в `.gitignore`) на стенде, а для
CI — в зашифрованных Secrets GitHub (`RC_KEYSTORE_BASE64`, `APP_PUBLISH_TOKEN`); в коде и
конфигурации — только обращение по имени переменной окружения.

**6. Чем непрерывная поставка отличается от непрерывного развёртывания? Зачем нужны
отдельные окружения?**

Непрерывная поставка (delivery) — каждое изменение в `main` автоматически доводится до
состояния «готово к выпуску», а выпуск запускает человек. Непрерывное развёртывание
(deployment) — изменение без участия человека сразу попадает в рабочую среду. У нас APK после
слияния собирается и публикуется на стенде автоматически, а сервер стенда пересобирается
вручную задачей — это поставка. Окружения dev (ноутбук разработчика), CI (временный стек в
GitHub Actions) и стенд (prod для демонстрации) нужны, чтобы проверять изменения на копиях,
не ломая систему, которой пользуются, и чтобы тестовые данные не смешивались с настоящими.

# Вывод

В проекте работает процесс «ветка → pull request → проверки → merge» с шаблоном PR и
ревью; три пайплайна GitHub Actions собирают и тестируют сервер, сборщик и приложение на
каждое изменение. По спецификациям лабораторной № 5 реализованы 23 автотеста, они
прогоняются в CI; на учебном PR показано, что намеренная ошибка делает сборку красной, а
исправление — снова зелёной. Секретов в репозитории нет; сервер упакован в Docker,
приложение поставляется на стенд автоматически после слияния.
